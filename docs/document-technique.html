Résumé

Document Technique RASP Platform

Runtime Application Self-Protection - Plateforme de détection, redaction, audit et blocage des attaques applicatives en temps réel.

Ce document présente l'architecture complète, les choix techniques justifiés et le guide d'intégration de la plateforme RASP, composée de trois repos distincts développés à partir d'un cahier des charges technique exigeant. Il est destiné à un tech lead ou un responsable sécurité souhaitant auditer l'implémentation ou intégrer l'agent dans une application Node.js.

🏗 rasp-platform
Control plane Next.js 16. Dashboard, backoffice, gestion des orgs/projets/agents, policies signées, API discovery, audit log, approvals, kill-switch.
📥 rasp-collector
Service Fastify 5 d'ingestion. Reçoit les événements des agents, authentifie (bcrypt + HMAC), valide, persiste en PostgreSQL partagé.
🛡 agent-node
Package npm @queno/agent-node. Middleware Express/Fastify/NestJS. 10 détecteurs, redaction locale, transport sécurisé, policy signée Ed25519.
Positionnement Un agent RASP s'installe dans le processus de l'application cliente et inspecte les requêtes HTTP à l'exécution, au plus près du code applicatif - contrairement à un WAF réseau qui opère à l'extérieur. Cela permet de détecter des attaques contextualisées (BOLA via JWT, injections dans des corps de requête chiffrés) que les solutions périmètriques ne voient pas.

Ce qui est livré (MVP fonctionnel)

  • 10 détecteurs d'attaques : SQLi, XSS, Command Injection, Path Traversal, NoSQLi, SSRF, Prototype Pollution, Template Injection, Suspicious Headers, BOLA
  • Moteur de redaction avec audit JSONL local - les données sensibles ne quittent jamais le processus client en clair
  • Intégrations Express, Fastify et NestJS prêtes à l'emploi
  • Distribution de policy Ed25519 signée depuis le dashboard (mode, rules custom, redaction config)
  • Collector avec auth bcrypt, HMAC-SHA256, rate-limiting par tenant, mTLS optionnel
  • Dashboard : lifecycle agents, canary rollout (0→1→10→50→100%), kill-switch global, approvals dual-auth
  • API Discovery passive avec heatmap auth, export OpenAPI, détection d'APIs shadow
  • Audit log à chaîne de hash + encryption au repos par tenant (AES-256-GCM)

Choix : dépendance unique (zod) L'agent est installé dans des milliers d'applications clientes. Minimiser la surface d'attaque de la supply chain est une priorité de sécurité : une seule dépendance runtime, utilisée uniquement pour la validation de configuration au démarrage. Crypto, buffer, fetch - tout est fourni par Node.js ≥18.

Logique d'Ingestion

ModuleComportement
persist-event.ts ① Chiffre metadata (si KEK) → ② Crée SecurityEvent (redacted=true) → ③ Si severity ∈ {critical, high} : crée Alert automatiquement.
persist-heartbeat.ts ① Charge agent → ② Lit en parallèle : policyVersion, targetVersion, kill-switch global, mode → ③ Met à jour Agent (heartbeat, status, version) → ④ Répond avec payload de contrôle.
resolve-target-version.ts Priorité upgrade : pin > canary FNV-1a > maintenance window UTC. Persiste upgradeStatus=upgrading à la transition.
persist-discovery.ts Upsert DiscoveredEndpoint sur (projectId, method, pathPattern). Cumule traffic/error counts, calcule riskScore, marque isShadowApi à la création.
volume-monitor.ts Fenêtre glissante 60s par projectId:agentId. Si count > seuil → crée événement abnormal_volume + Alert. Cooldown 5 min. Swallows ses propres erreurs.
get-policy.ts Lecture seule. Retourne verbatim la Policy signée la plus récente pour le channel. Le collector ne signe jamais.
Justification : 202 Accepted pour l'ingestion Le pattern 202 signale "accepté pour traitement" même si la persistence est aujourd'hui synchrone. Il découple contractuellement le protocole agent de l'implémentation interne du collector : une migration vers un bus asynchrone (Redis/BullMQ) ne changera pas le contrat HTTP des agents.
Justification : collector comme relais de policy Le collector sert les policies signées verbatim sans re-signer. La compromission du collector ne peut pas forger une nouvelle policy : seul le control plane (rasp-platform) détient la clé privée Ed25519.

Intégration Express

import express from "express";
import { RaspAgent, createExpressMiddleware } from "@queno/agent-node";

// 1. Instancier et démarrer l'agent AVANT app.use()
const agent = new RaspAgent({
  apiKey:    process.env.RASP_API_KEY!,
  projectId: process.env.RASP_PROJECT_ID!,
  agentId:   process.env.RASP_AGENT_ID!,
  framework: "express",
  mode:      "monitor",  // ou "block"
});
agent.start();

const app = express();
app.use(express.json());
app.use(express.urlencoded({ extended: false }));

// 2. Monter le middleware APRÈS les body parsers
app.use(createExpressMiddleware(agent));

// 3. Vos routes
app.get("/api/users/:id", (req, res) => {
  // Si mode block et attaque détectée, le middleware a déjà répondu 403
  res.json({ id: req.params.id });
});

// 4. Drain propre à l'arrêt
process.on("SIGTERM", async () => {
  await agent.stop();  // flush buffer + ferme audit log
  process.exit(0);
});

app.listen(3000);TypeScript
Ordre critique : body parsers avant le middleware RASP Le middleware doit être monté après express.json() / express.urlencoded() pour que le corps de la requête soit disponible lors de l'inspection. Monter l'agent avant les parsers ne plante pas l'application (fail-open) mais le corps ne sera pas inspecté.

Modes, Lifecycle & Kill-switch

SujetComportement
monitor Mode par défaut. Les attaques sont détectées et reportées. Toutes les requêtes passent - le middleware appelle toujours next().
block Si une attaque est détectée, le middleware répond HTTP 403 { "error": "Request blocked by RASP", "eventType": "..." } et n'appelle pas next().
Lire le mode courant Utiliser agent.mode (pas la config de démarrage). Le mode peut changer via policy signée depuis le dashboard.
agent.start() Démarre le heartbeat (immédiat puis périodique), l'instrumentation DB si activée, self-protect si activé.
agent.stop() Async. Arrête heartbeat + self-protect, drain le buffer d'événements, drain la discovery, ferme le fd d'audit log.
Kill-switch Si killSwitch: true dans la réponse heartbeat : inspect() et beginRequest() deviennent des no-ops immédiats. L'heartbeat continue (pour détecter la levée du kill-switch). Récupération automatique si killSwitch repasse à false.
Fail-open Toute exception dans inspect(), détecteurs, transport, audit log est swallowée. L'agent ne peut jamais faire crasher l'application hôte.

Moteur de Redaction (src/redaction/)

engine.ts - deux passes

  • Key-based (denylist) : clés d'objet correspondant aux patterns → sous-arbre remplacé par [REDACTED]. Profondeur max 6 niveaux.
  • Value-based : les valeurs string sont scannées par redactValueString(). Configurable via valueRedaction (défaut true).
  • Mode allowlist : redacte tout sauf les clés structurelles autorisées + allowKeyPatterns.

Invariants de sécurité de l'agent

Invariant 1 - Redaction avant buffer Aucun payload n'entre dans le buffer de transport avant d'avoir passé la redaction. Si la redaction throw, l'événement est abandonné (pas envoyé). Le fait est journalisé localement avec dropped: true.
Invariant 2 - Fail-open ≠ fail-closed Fail-open s'applique à l'impact sur l'application hôte (une exception dans l'agent ne crash jamais l'hôte). Fail-closed s'applique à la fuite de données (échec redaction = abandon événement). Ce sont deux garanties orthogonales.
Invariant 3 - Audit local ≠ télémétrie distante L'audit JSONL (rasp-audit.log) reste dans l'environnement client. Il n'est jamais transmis au collector. Il ne contient que des métadonnées de redaction (champs redactés, type d'événement) - jamais les valeurs brutes.

Ce que l'agent ne fait jamais

  • N'envoie jamais de mots de passe, tokens, clés API ou headers Authorization en clair.
  • N'envoie jamais de corps de requête brut par défaut.
  • Ne fait jamais d'appels réseau arbitraires - uniquement vers l'URL collector configurée.
  • Ne stocke jamais la clé API en clair dans le heap (SecureStore AES-GCM).
  • Ne fait jamais crasher l'application hôte quelle que soit l'erreur interne.

Priorité haute - sécurité & fiabilité

Architecture & Scalabilité

File d'attente asynchrone côté collector La persistence des événements est aujourd'hui synchrone dans le path HTTP. Pattern recommandé : validation → enqueue → 202 → worker → persist.

Causes de rejet communes

Annexe D - Glossaire

TermeDéfinition
RASPRuntime Application Self-Protection. Protection de sécurité embarquée dans le processus de l'application, qui analyse les requêtes à l'exécution.
WAFWeb Application Firewall. Protection périmètrique réseau (niveau infrastructure, avant l'application). Complémentaire au RASP mais ne voit pas le contexte applicatif.
Monitor modeMode par défaut. Les attaques sont détectées et reportées, mais les requêtes passent. Aucun impact sur le flux normal.
Block modeMode actif. Les requêtes détectées comme attaques sont bloquées (HTTP 403). À activer après validation en monitor.
Fail-openEn cas d'erreur interne de l'agent (exception, collector indisponible), l'application hôte continue de fonctionner normalement. L'agent ne peut jamais provoquer une interruption de service.
Fail-closedEn cas d'échec de la redaction, l'événement est abandonné (non transmis). Priorité donnée à la confidentialité des données sur la complétude de la télémétrie.
BOLABroken Object Level Authorization. Attaque où un utilisateur accède aux ressources d'un autre utilisateur en manipulant les IDs dans l'URL (ex: /api/users/2 avec le JWT de l'utilisateur 1). Aussi appelé IDOR.
Policy signéeConfiguration distribuée aux agents (mode, règles, redaction) signée Ed25519 par le control plane. Les agents vérifient la signature avant d'appliquer toute policy.
Trust anchorClé publique Ed25519 que l'agent considère comme autorité de confiance pour les policies. Configurable via RaspConfig.policyPublicKey ou RASP_POLICY_PUBLIC_KEY.
ChannelCanal de distribution des policies et versions : stable (défaut), early (preview), edge (cutting edge). Permet un déploiement progressif par cohorte.
Kill-switchMécanisme d'arrêt d'urgence. Par agent (dashboard) ou global (backoffice, dual-auth). L'agent en kill-switch ne détecte plus rien mais continue les heartbeats pour détecter la levée.
Canary rolloutDéploiement progressif d'une version agent : 0 → 1 → 10 → 50 → 100% des agents. Cohort déterministe par FNV-1a sur agentId. Auto-halt sur dépassement de budget d'erreur.
DEK / KEKData Encryption Key (par projet) / Key Encryption Key (master). Le DEK chiffre les données au repos ; le KEK chiffre le DEK. Crypto-shred = suppression du DEK → données inaccessibles.
HMAC-SHA256Hash-based Message Authentication Code. Garantit l'intégrité et l'authenticité du payload transmis par l'agent. Calculé sur les bytes exacts du body (req.rawBody).
SecureStoreComposant de l'agent qui chiffre les secrets (apiKey, hmacSecret) en mémoire avec une clé AES-256-GCM aléatoire par processus. Résistance aux heap dumps.
API DiscoveryObservation passive des endpoints HTTP appelés à l'exécution. Permet de détecter les APIs shadow (non documentées) et zombie (inactives).
Dual authorizationSéparation des responsabilités (4-eyes principle). Une action critique nécessite qu'un admin la demande ET qu'un second admin différent l'approuve.
Audit chainChaîne de hash SHA-256 sur les entrées d'audit log. Chaque entrée porte le hash de la précédente. Toute modification rétroactive brise la chaîne.
mTLSMutual TLS. Authentification bidirectionnelle : le serveur et le client présentent chacun un certificat. Couche d'authentification supplémentaire au niveau réseau.
